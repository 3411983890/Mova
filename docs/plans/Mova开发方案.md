# Mova 开发方案

> 版本：0.1｜整理日期：2026-11-09  
> 本文汇总现有讨论，并结合项目中的界面原型制定实施建议。技术选型和范围标记为建议，尚未验证的能力不能视为已实现。

## 1. 产品定位

Mova 是一个以 AI Agent 为核心的工作台，让用户在同一个应用中进行对话、编程、设计和电脑操作。长期目标是由用户提出任务，Agent 调用合适的模型与工具，展示过程、产物和结果，并在需要时交由用户接管。

产品优先面向 Windows 桌面；未来可考虑 macOS、Linux 和浏览器。ChatMova、CodeMova、Dot 和 Design 共用会话、项目、模型设置和任务记录；具体命名与入口仍可调整。

## 2. 当前项目现状

项目已有基于 Vite 的 HTML、CSS、JavaScript 界面原型，部分输入区使用 React 组件。原型包含 ChatMova / CodeMova 切换、侧栏、项目与聊天列表、输入区、模拟执行过程、用量面板及待机小球。

项目、会话和文字消息已可保存到本地。Windows 桌面外壳与标题栏窗口控制已接入，浏览器预览仍可用。桌面聊天在 Electron 主进程中运行 Pi Agent，通过本机接口完成流式回复、AnySearch 网页搜索和用户上传的图片理解。CodeMova 已可按文件夹授权读写项目文件并执行命令；独立 Agent 进程、变更预览面板和 SQLite 尚未接入。详细运行方式和已有能力以项目 `README.md` 为准，权限模型见 `Mova权限设计.md`。

**开发原则：保留已确认的视觉设计与交互，逐步将原型迁移到可维护的组件结构，不把模拟能力描述为已经上线。**

## 3. 功能规划

| 模块 | 目标 | 首版范围 | 后续扩展 |
| --- | --- | --- | --- |
| ChatMova | 与 AI 对话，查看任务过程与结果 | 模型配置、流式聊天、会话保存、停止生成 | 附件、多模态、跨会话检索 |
| CodeMova | 在项目中理解和修改代码 | 选择目录、文件列表、受控读写、变更预览 | 编辑器、终端、Git、测试与多代理 |
| Dot | 执行跨工具、多步骤任务 | 展示任务状态、步骤和授权请求 | 长期任务、调度、记忆与子代理 |
| Design | 辅助设计界面与视觉内容 | 预留工作区、展示设计产物 | 验证设计工具接入、画布编辑与导出 |
| Computer | 操作网页和桌面 | 先验证浏览器操作 | 桌面控件、视觉兜底、远程电脑 |
| Mobile | 操作 Android 应用 | 暂不纳入首版 | 模拟设备、云手机、实体设备 |

## 4. 推荐技术架构

```text
Mova 桌面客户端（Electron）
  ├─ 界面：React + TypeScript + Vite
  │    └─ 工作区、聊天、项目、设置、任务过程
  ├─ 桌面主进程 / 安全桥接
  │    └─ 窗口、文件选择、系统能力、后台进程管理
  └─ Agent 服务（独立进程）
       ├─ Pi 适配层 + 模型提供商适配层
       ├─ 会话、任务和权限管理
       ├─ 工具与 MCP 管理
       └─ Browser / Desktop / Mobile 执行器
```

- **前端**：推荐 React、TypeScript、Vite。UI 状态可用 Zustand；异步数据管理可按实际复杂度引入 TanStack Query。保留现有 CSS，逐步建立颜色、间距、字号等设计变量。
- **桌面外壳**：推荐 Electron，先以 Windows 为目标。通过受控的 preload 接口暴露必要能力，界面不直接获得 Node 或系统权限。Tauri 可作为后续备选，需权衡 Rust 和系统 WebView 差异。
- **Agent 服务**：推荐独立于界面运行，使用 Pi 作为待验证的核心候选；模型、工具和任务调度通过适配层连接，避免界面依赖某个 SDK 的内部实现。Pi 和各模型的实际接口、版本、许可证在接入前核验。
- **通信**：桌面端先通过受限 IPC 与本地服务通信；流式输出采用事件通道。未来远程服务可增加经过认证的 API / WebSocket，不在第一阶段引入不必要的网络部署。
- **存储**：首版用本地 SQLite 保存会话、消息和任务索引；附件单独存放，数据库只记录元数据与路径。云同步、多用户和加密方案后续单独设计。

### 4.1 数据流

1. 用户选择模式、模型和工作目录，提交消息。
2. 前端通过统一客户端接口发送请求，创建任务并显示运行状态。
3. Agent 服务组装上下文，调用模型和经授权的工具。
4. 服务流式返回文本、工具事件、授权请求和错误。
5. 前端展示过程；完成后保存消息、任务状态和产物引用。
6. 用户可停止任务；中断后记录真实状态，避免误报完成。

建议事件至少包含 `taskId`、事件类型、时间和顺序编号，覆盖文本增量、工具开始 / 结束、审批、错误、完成和取消。重连时按编号补齐，避免重复显示。

## 5. 前端迁移方案

1. **固定基线**：保留现有原型，记录关键页面、截图和交互；先不大规模重写。
2. **搭建 React 入口**：沿用 Vite，创建 TypeScript 入口；让原 HTML 的静态布局逐步进入 React。
3. **按区域迁移**：先迁应用外壳与侧栏，再迁聊天列表、消息流、输入区、弹窗和工作区。一次迁一个区域，持续对照视觉效果。
4. **抽取状态**：将模式、项目、会话和布局状态从 DOM 操作移到组件与状态层；区分临时界面状态和应持久化的数据。
5. **隔离数据来源**：定义 `MovaClient` 接口，先用模拟实现，接入后台时替换实现。示例数据应明确标记，不能与真实记录混淆。
6. **验证**：检查窗口缩放、键盘操作、深浅色、长消息和窄窗口。现有外部组件及素材的许可信息继续保留。

建议目录（迁移时逐步建立，非现有目录）：

```text
src/
  app/           应用入口与整体布局
  components/    共用基础组件
  features/      chat、code、dot、design、settings
  services/      客户端接口、模拟实现与真实实现
  stores/        界面状态
  styles/        设计变量及全局样式
electron/        主进程与 preload
agent/           Agent 服务及工具适配
```

## 6. Agent、模型与工具

### 6.1 Agent 核心

桌面聊天使用 Pi Agent Core 执行模型与工具循环，Pi AI 负责本机 OpenAI 兼容接口，Mova 负责工作区、任务状态、密钥、图片和交互。首个注册工具为 AnySearch 网页搜索。CodeMova 在用户按文件夹授权后额外暴露文件读写与命令工具（`list_files`、`read_file`、`write_file`、`replace_in_file`、`run_command`），工具可见性与执行都以主进程的权限存储为准；ChatMova 不开放文件工具。MCP 与终端会话尚未接入。

模型层设计统一接口，逐步接入用户所需的 DeepSeek、OpenAI、Claude 等服务；各提供商的能力、计费、工具调用和图像支持不同，应按实际配置展示。密钥存放在系统凭据存储或受保护的服务端，避免写入前端代码、日志或仓库。

### 6.2 工具层候选

| 能力 | 候选 | 接入阶段 |
| --- | --- | --- |
| 浏览器 | Playwright MCP | 首个工具原型 |
| 电脑操作 | Microsoft Hybrid Computer Use 等 | 浏览器闭环稳定后做兼容性验证 |
| 设计 | OpenPencil MCP | Design 阶段验证实际集成方式 |
| 手机 | Mobile MCP | Android 阶段验证 |
| 代码协作 | GitHub MCP | 根据 CodeMova 需求接入 |
| 文档检索 | Context7 | 按需接入 |

这些均为候选，不代表已集成。按模式、任务和用户授权加载工具，避免工具重复和过多上下文。安装前审查权限、依赖、许可证、运行成本及 Windows 兼容性。

### 6.3 混合操作策略

优先使用合适的专用 API 或结构化工具；网页优先 DOM / 无障碍信息，桌面优先 UI Automation，无法可靠定位时再尝试视觉截图与坐标操作。每次关键操作后重新观察目标状态；结构化与视觉操作应指向同一设备和会话。

权限不足、验证码、登录验证或不可判断的高风险操作应暂停并交给用户，不因出错而无条件切换视觉。设置超时、重试上限，处理截图缩放和坐标映射，避免重复执行有副作用的操作。

## 7. 数据、权限与安全

- 会话、消息、任务、工具事件、项目、配置和产物分别建模；保存必要的状态、时间、关联 ID、错误和版本信息。
- 工作目录、网络、工具和设备访问应有明确授权范围；删除、发送、支付等有外部影响的动作依据产品策略要求用户确认。
- 外部网页、文件和工具返回内容属于不可信输入，不能直接改变系统权限或覆盖用户授权。
- 执行环境与界面隔离；工具调用记录必要的审计信息，对密钥、敏感内容进行脱敏。
- 云电脑和多用户阶段单独设计身份、租户隔离、资源回收、网络边界、备份与费用控制；不要把首版单用户模型直接当作生产级多租户方案。

## 8. 云电脑与 Android 规划

Browser、Desktop 和 Mobile 使用独立 Provider，使 Agent 通过统一能力接口访问不同环境。先在本地完成任务生命周期和浏览器闭环，再验证 Windows 云电脑的连接、画面传输、权限和断线恢复。

Android 可评估 redroid、商业云手机和实体设备。容器或模拟设备不保证所有应用兼容，也不等同于通过设备认证的实体手机；先根据目标 App 进行验证。手机画面嵌入需要视频流、输入映射、认证与延迟处理，不能简单视为已有桌面窗口的直接嵌入。

## 9. 分阶段实施与验收

### 阶段 0：整理原型

- 确认工作台布局和 ChatMova / CodeMova 的关键界面；记录设计变量及现有素材许可。
- 验收：主要页面可在浏览器运行，视觉基线和演示边界清楚。

### 阶段 1：前端和桌面外壳

- 按区域迁移至 React / TypeScript；接入 Electron 基础窗口，建立模拟客户端接口。
- 验收：Windows 桌面启动、缩放与关闭正常；核心界面与原型一致，刷新及失败状态清晰。
- 当前进度：已接入 Electron 基础窗口，建立 TypeScript 入口并迁移窗口控制区和聊天记录；已建立模拟消息服务接口。侧栏等区域仍沿用原型实现。

### 阶段 2：真实聊天 MVP

- 接入一个模型提供商和 Pi 最小验证；实现流式消息、停止、配置和本地会话持久化。
- 验收：可创建会话、发送消息、查看真实回复、停止请求，重启后恢复记录；网络错误有明确提示。
- 当前进度：桌面版已通过 Pi 接入本机模型，支持模型与思考强度选择、流式回复和停止；真实模型思考、AnySearch 来源和上传图片复用原有思考界面。SQLite 存储尚未接入。

### 阶段 3：CodeMova 与首个工具

- 接入工作目录、文件读取、变更预览和受控写入；验证一个浏览器工具。
- 验收：限定目录内完成一项小型代码任务，用户可检查变更；权限拒绝、工具失败和取消均有正确状态。
- 当前进度：已接入工作目录（原生选择器登记，按文件夹授予读取 / 修改 / 执行）、受控写入与命令执行、逐次原生确认、会话级允许、撤销与审计日志；变更预览面板、删除/移动工具、Git 集成和浏览器工具尚未接入。

### 阶段 4：Dot 与混合电脑操作

- 实现任务状态、执行事件、授权与人工接管；验证网页语义操作，再尝试桌面及视觉兜底。
- 验收：在指定测试环境完成可重复的任务，记录成功率、耗时、模型 / 截图调用数与失败原因。

### 阶段 5：Design、云端与 Mobile

- 分别验证设计工具、远程桌面和 Android；成熟后按用户需求加入产品。
- 验收：每种接入均有明确兼容范围、权限边界、成本和失败恢复方式。

阶段顺序为建议，不承诺工期；每阶段先完成可演示闭环，再扩展能力。

## 10. 建议优先处理的决定

1. 确认首版平台是否只做 Windows，以及是否需要同时支持网页版。
2. 选择首个模型提供商与密钥配置方式。
3. 明确首版主场景：聊天优先，还是需要同时完成一个 Code 任务。
4. 确认 CodeMova 对本地文件的授权、变更预览和执行策略。
5. 确定 Dot、Design 的首版入口是否仅展示规划，避免误导用户。
