# Mova 设计规范

版本：1.1 · 基于当前界面原型整理 · 2026-11-10

## 1. 文档用途与使用方式

本规范为 Mova 后续的产品设计、前端开发和验收提供统一依据。适用于桌面端 ChatMova、CodeMova、设置、聊天与输入等界面。它描述视觉规则，也描述状态、动效、响应式和交互约束。

**状态标记**：

- **现状**：可在当前源码中找到的值或行为，反映原型截至本文日期的实现。
- **目标**：为后续统一体验提出的设计决策；尚不代表已经实现，也不应未经验证就覆盖现有页面。
- **待设计**：目前没有足够依据定义成已完成的能力，开发前需结合具体场景补全。

所有尺寸默认是 **CSS 像素**，不是截图像素、设备物理像素。示例中的参数是设计依据，不保证第三方组件内部已完全遵守。颜色均为不透明 sRGB，带透明度的颜色另行标注。实际视觉以浏览器渲染为准。

**组件专属规范**：设置页（配置、使用情况、模型、记忆与存储、已归档的聊天）的骨架、内容列、间距、颜色、控件与验收清单见 [Mova设置页设计规范.md](Mova设置页设计规范.md)；对话页（消息流、执行过程、Markdown、事件协议）见 [Mova对话页设计规范.md](Mova对话页设计规范.md)。两者冲突时，按 1.1 的优先级以组件规范为准。

### 1.1 优先级

1. 用户明确提出的具体需求和已确认的设计稿。
2. 组件专属规范。
3. 本文的语义 token 和通用规则。
4. 现存代码中的历史数值。发生冲突时先确认是否是有意保留的差异，再安排迁移。

### 1.2 设计目标

- **安静、专注**：聊天内容是主角，导航、工具与边框退后。
- **清晰的层次**：靠位置、间距、文字权重及细微背景变化区分层级，避免每个元素都做成卡片。
- **工具感而非装饰感**：图标克制，信息密度适中，动效服务于状态变化。
- **交互可预测**：同类控件的外形、操作、反馈和关闭方式一致。
- **中文优先但支持混排**：中文、英文、路径和代码混排时可读、不破坏布局。
- **操作可访问**：鼠标、键盘、触屏和减少动态效果模式都能完成主要操作。

## 2. 产品结构与视觉层级

### 2.1 从外到内

1. **窗口外壳与标题栏**：承载窗口操作和全局入口，视觉最安静。
2. **活动栏**：承载跨模块导航；选中的入口可用背景和图标亮度区分。**设置覆盖层打开时，活动栏不保留任何选中项**（同时移除 `aria-current`），关闭后恢复到打开前的选中入口——设置本身不是活动栏的模块，不应让「主页」继续显示为当前页。
3. **项目 / 聊天侧栏**：承载模式切换、搜索、项目与会话列表。
4. **主内容区**：欢迎页、聊天内容或设置，是注意力中心。
5. **浮层**：详情、菜单、选择器、对话框。通过边框、背景、阴影和位置区分，而非仅靠强烈亮度。

### 2.2 两种模式

| 模式 | 信息结构 | 关键规则 |
| --- | --- | --- |
| ChatMova | 所有聊天平级排列 | 不显示文件夹层级；聊天行之间保持 2px 间隔 |
| CodeMova | 项目 → 聊天 | 项目行显示文件夹；聊天向右缩进；新聊天时可显示项目 / 计算机上下文 |

同一种聊天的选中态、归档操作、详情卡及键盘操作在两个模式下保持一致。

**模式切换浮层**（点「ChatMova ⌄」展开）：宽度取侧栏的 **62.7%**（居中，左右各留 18.7%），标题 `18 × var(--u)`、说明 `15 × var(--u)`、内边距 `8 × var(--u)`、圆角 `19 × var(--u)`；相对旧版整体缩到 2/3。它只是模式选择，不承载其他操作，也不跟随侧栏变宽而铺满。

## 3. 色彩系统

### 3.1 使用原则

- 所有新组件优先引用**语义 token**，不要直接按“灰一点”“亮一点”任意添加近似色。
- 背景、边框、文字、图标和状态分别命名。同一个色值可暂时服务多个语义，但不要因此把语义合并。
- 在相同表面上，保持正文、次要信息、禁用状态有明确层级；不能只依靠亮度表达错误或选中。
- 带文字的颜色组合必须按实际背景校验对比度；下面列出的历史色值不是对比度合格证明。
- 同一控件的 hover、selected、focus 可叠加；焦点指示不能被选中背景代替。

### 3.2 基础表面与内容色

| 建议 token | 色值 | 用途 | 状态 / 对应现状 |
| --- | --- | --- | --- |
| `--color-canvas` | `#181818` | 聊天主画布、主要工作区底色 | 现状：`--canvas` |
| `--color-sidebar` | `#161616` | 项目 / 聊天侧栏底色 | 现状：`--menu-bg` |
| `--color-preview` | `#161616` | 聊天详情悬停卡 | 现状：`.chat-preview` |
| `--color-shell` | `#202020` | 窗口外壳、活动栏基础色 | 现状：`--shell`；窗口聚焦时另有 `#0d0d0d` |
| `--color-surface` | `#212121` | 项目菜单、聊天操作菜单表面 | 现状 |
| `--color-surface-raised` | `#2e2e2e` | 输入区模型与用量等较高层浮层的回退色 | 现状：输入组件主题回退值 |
| `--color-message-user` | `#2f2f2f` | 用户消息气泡 | 现状 |
| `--color-text` | `#d6d6d6` | 通用界面文字 | 现状：`--text` |
| `--color-text-strong` | `#f3f3f3` | 助手回复正文等重点文字 | 现状 |
| `--color-text-muted` | `#868686` | 次要标签与低强调图标 | 现状：`--muted`；小字需复核对比度 |
| `--color-border` | `#2f2f2f` | 主框架和安静分隔线 | 现状：`--line` |
| `--color-border-raised` | `#393939` | 项目菜单边框 | 现状 |
| `--color-focus` | `#5b9bf0` | 键盘焦点环 | 现状 |

**色彩模型**：背景与界面层为**无彩色**（R=G=B，纯黑灰阶梯），不再带绿/青色调；强调色统一为**蓝色**（`--color-accent-info` `#3795f5`、`--color-primary-action` `#2f6bd8`），用于焦点环、链接、主操作和选中指示。新增色值时必须先在其中一档阶梯上取近似值，不要引入新的色相。

**注意**：`#161616` 的详情卡可以和侧栏同色；仍需要边框和阴影将卡片与后面的内容区分开。输入组件位于独立样式作用域，不能假设它自动继承外层所有变量。

### 3.3 状态与语义色

| 建议 token | 色值 / 处理 | 使用时机 | 禁止 / 注意 |
| --- | --- | --- | --- |
| `--color-hover` | `#2d2d2d` | 通用悬停底色 | 不把悬停当成持久选中 |
| `--color-list-selected` | `#292929` | 项目或聊天当前选中项 | 同时用语义状态标记当前项 |
| `--color-list-hover` | `#272727` | 聊天行悬停或键盘操作状态 | 与选中叠加时需保留当前项识别 |
| `--color-overlay-hover` | `#ffffff12` | 小图标按钮、菜单项的低强度悬停叠层 | `12` 为十六进制透明度，不是不透明白 |
| `--color-accent-info` | `#3795f5` | 用量进度等信息性强调 | 不用作所有普通文字颜色 |
| `--color-notification` | `#2d6acb` | 通知点 | 状态信息应有文字或无障碍名称 |
| `--color-danger` | `#e0928c` | 移除、永久删除等破坏性文字 / 图标 | 归档是可恢复操作，不自动视为危险操作 |
| `--color-danger-hover` | `#c74242` | 当前窗口关闭按钮悬停 | 仅用于该场景；其他危险按钮单独验证 |
| `--color-primary-action` | `#2f6bd8` | 主要提交动作（设置、Bot 创建等） | 需校验文字对比度；悬停现状为 `#3a7ae8` |
| `--color-disabled` | 待验证 | 真正不可操作的控件 | 不仅降透明度；保留可读名称和原因 |
| 成功 / 警告 | 待设计 | 成功、警告反馈 | 目前没有经验证的全局语义色，不自行沿用蓝色或红色 |

### 3.4 状态优先级（目标）

默认 → 悬停 / 按下 → 选中 / 展开；键盘焦点环独立叠加在这些状态之上。禁用态不触发 hover 或点击反馈。危险操作的语义色应在 hover 和 focus 下保持可辨识。

### 3.5 遮罩、阴影和边框

- 浮层边框一般为 **1px**，使用与表面相邻但可见的低对比边框；不能只依赖阴影区分边界。
- 详情卡现状阴影 `0 12px 28px #0005`；项目菜单现状 `0 20px 44px #0008`；输入区现状 `0 8px 24px #0004`，聚焦时为 `0 10px 30px #0006`。
- 对话框现状遮罩为 `#0008`。同层弹窗不要重复叠加遮罩。
- **目标**：同类浮层统一使用同一档阴影；小详情卡用轻阴影，菜单与模态对话框用更明显阴影。不要为每个组件发明一套。

## 4. 排版

### 4.1 字体

现状字体栈：`"Segoe UI", "Microsoft YaHei UI", "Microsoft YaHei", Arial, sans-serif`。沿用系统字体，不为装饰性目的随意更换。代码、命令、路径等需要等宽对齐时，使用系统等宽字体并提供中文回退；避免把普通中文界面整体设为等宽。

### 4.2 字号与行高

| 用途 | 现状 / 目标 | 字重 / 行高 |
| --- | --- | --- |
| 欢迎语 | 现状 `clamp(23px, 2.2vw, 36px)` | 400 / 1.4 |
| 聊天顶部标题 | 现状 15px | 600 |
| 助手正文 | 现状 14px | 500 / 1.7 |
| 用户消息 | 现状 14px | 默认字重 / 1.6 |
| 列表、菜单、次要说明 | 按组件；菜单现状 12px | 常规或 500；避免靠过粗字重强调所有信息 |
| 辅助数据、时间 | 现状常见 11–12px | 使用低强调色，但必须验证对比度 |
| 对话框标题 | 现状 22px | 按标题层级设置 |

侧栏部分尺寸使用 `--u: clamp(.58px, calc(100vw / 2600), .69px)` 换算，不能将 `calc(23 * var(--u))` 当成 23px。**目标**：逐步迁移为明确的字体 token 和响应式规则，避免不同屏宽下文字过小。

### 4.3 文本规则

- 界面文案使用简短、直接的中文；按钮以动词或动词短语命名，例如“新建项目”“归档”。
- 明确动作范围。项目菜单中的“归档”应通过项目上下文和必要的辅助说明让用户知道它影响该项目的聊天；高影响批量操作的确认与撤销属于后续产品设计，不假定原型已具备。
- 列表标题单行省略；鼠标悬停可滚动长标题并显示详情卡，键盘用户也应能取得完整标题。
- 聊天正文保留自然换行；长链接、路径、无空格长串允许换行，不能撑破容器。
- 英文、数字和中文混排避免强制在每个字符之间插入空格；数字单位和时间格式保持全站一致。
- 不用全大写或大面积粗体制造层级；优先使用位置、字号和间距。

## 5. 间距、尺寸与对齐

### 5.1 基础间距刻度

| Token | 值 | 推荐用途 |
| --- | --- | --- |
| `space-0` | 0 | 重置默认间距 |
| `space-0.5` | 2px | 紧凑列表行之间；微小元素间距 |
| `space-1` | 4px | 图标与紧密标签、控件内部微调 |
| `space-2` | 8px | 图标与文字、紧凑组件间距 |
| `space-3` | 12px | 小浮层内边距、普通控件间距 |
| `space-4` | 16px | 常规面板内边距、相关区块 |
| `space-5` | 24px | 聊天轮次、较大区块分隔 |
| `space-6` | 32px | 页面级留白，目标 |

现状已定义 4 / 8 / 12 / 16 / 24px；2px 列表间距来自现有侧栏实现。必要的 5、6、7、10、14px 等历史微调应限于组件内部，不应扩散为无语义的全局刻度。

### 5.2 对齐原则

- 同一级元素共用左边缘；项目图标与上方“新项目”图标视觉对齐。
- 侧栏列表悬停 / 选中背景的左右留白保持对称，并考虑滚动条占位和不同浏览器的滚动条宽度，不把某一平台的滚动条宽度视为可靠常量。
- CodeMova 子聊天的标题相对项目名称缩进；聊天行归档图标与项目行的新建对话图标对齐。
- 右侧图标使用固定操作区，悬停时不挤压、跳动标题。活动栏图标以各自按钮中心对齐。
- 相邻聊天行至少留出 2px；边框和高亮不得视觉粘连。
- 正文、标题、图标按视觉中心微调，不能只凭数学中心判断。

### 5.3 建议点击区域

桌面密集工具栏在不改变视觉图标大小的前提下，目标交互区域不小于 24 × 24px；触屏优先使用至少 44 × 44px 或满足等效间隔。现状中部分控件更小，应在迁移与验收时检查。视觉尺寸和实际命中区域可不同，但不可覆盖相邻操作。

## 6. 圆角

| 场景 | 现状 / 目标 | 用法 |
| --- | --- | --- |
| 列表行、菜单项 | 现状 8px | 选中 / 悬停背景、菜单项 |
| 小菜单、详情卡 | 现状 12px | 聊天详情和项目菜单 |
| 消息气泡 | 现状 15px | 用户消息 |
| 输入区模型 / 用量浮层 | 现状 14px | 保持输入组件内部一致 |
| 项目对话框 | 现状 18px | 模态容器 |
| 消息输入框 | 现状 28px | 大型输入表面 |
| 圆形按钮 / 图标容器 | 50% | 发送、圆形加号等 |

圆角由组件层级决定：小控件较小，大表面较大。不要把 28px 输入框圆角套用到列表行，也不要因为相邻元素而强行要求所有圆角相同。

## 7. 图标

- 应用外壳及动态侧栏优先使用 `@keyline-icons/react`，统一通过 `icons.js` 的映射调用；第三方输入组件的图标系统是现有例外，后续应在视觉验收后逐步对齐。
- 使用同一风格的线性图标，优先保持轮廓、描边和视觉重量一致；选中状态可使用填充图标，但必须在该导航组内一致。
- 常规菜单图标现状约 16px；图标按钮应保证稳定对齐及足够命中区域。
- 项目使用文件夹图标；新建项目内聊天使用**圆形加号**；聊天行使用**归档图标**直接归档；项目菜单继续使用三个点。
- 不用图标替代唯一可见说明：仅图标按钮必须有准确的 `aria-label`；可以补充 `title`，但 `title` 不能代替无障碍名称。
- 图标颜色默认弱于主要文本，hover 时可提亮；危险操作图标与危险文字保持同一语义。

## 8. 核心组件规范

### 8.1 项目与聊天列表

**项目行**

- 左侧为文件夹图标与名称；点击行主体展开 / 收起项目。
- 右侧是项目菜单和新建聊天；鼠标悬停或键盘聚焦时显示，触屏设备应始终可发现。
- 两个操作保持间距，新建图标位于最右；不把菜单按钮包进主按钮，避免嵌套交互元素。
- 当前项目可显示轻微选中底色；行本身、操作按钮、焦点态分别可辨。

**聊天行**

- 默认显示名称；过长时省略。悬停时显示归档按钮，单击归档；触屏上操作需要可见。
- 当前聊天使用选中背景；`aria-current` 表达当前项。聚焦与悬停不应抹掉当前状态。
- 详情卡提供完整标题、位置（本地 / 云端）与项目名；其内容按数据真实情况显示，不把原型示例当作真实状态。
- 鼠标悬停长标题时可自动水平移动到末尾；移开还原。详情卡在右侧靠近对应行，空间不足时避开视口边缘。键盘访问可显示详情但不要求自动滚动。
- 归档为可恢复操作；后续接入真实数据时需要提供明确反馈，并设计恢复路径。当前原型在设置里的已归档聊天提供恢复。

### 8.2 详情卡、菜单和对话框

| 类型 | 触发 / 关闭 | 现状尺寸与位置 | 内容与限制 |
| --- | --- | --- | --- |
| 聊天详情卡 | 悬停 / 键盘焦点；移出、失焦、滚动关闭 | 宽 `min(209px, 100vw - 20px)`；优先在聊天行右侧 3px | 背景 `#141718`；展示完整内容；不是交互菜单 |
| 项目菜单 | 点击项目三个点；点击外部或 Escape 关闭 | 最小宽 164px；优先靠触发按钮右侧 6px | 操作项按含义分组，危险项使用危险色 |
| 输入区选择 / 用量浮层 | 点击对应控件；按组件行为关闭 | 用量面板现状宽 364px，上限 `100vw - 32px` | 与输入区主题和动画联动 |
| 模态对话框 | 用户主动发起；取消、关闭或 Escape | 项目对话框最大宽 420px、视口左右至少 16px | 遮罩、标题、字段、主次操作明确 |

菜单项现状 12px 字号、最小高度 28px；项目菜单的长文案决定最小必要宽度。详情卡宽度按内容换行，不裁掉关键信息。所有浮层须在视口内重新定位，不能只写死右侧坐标。浮层不应遮挡触发项或溢出窗口；空间不足时切换方向、限制最大高度并允许滚动。

**键盘目标**：菜单触发器提供展开状态；打开后焦点进入菜单；方向键按菜单模式移动，Escape 关闭并将焦点还给触发器。对话框应限制焦点在弹窗内，关闭后恢复焦点。当前各菜单实现存在差异，开发时需要逐项补齐，不能仅凭外观认定已实现。

### 8.3 消息与聊天内容

- 内容列现状最大宽度 `718px`，较窄视口使用 `calc(100% - 48px)`；居中显示。
- 用户消息靠右，最大宽度 80%，背景 `#2e302e`，内边距 10px 14px，圆角 15px。
- 助手正文靠内容列左侧，不强行放入气泡；字号 14px、行高 1.7。聊天轮次间距现状 24px。
- 工具 / 思考过程使用次级文字和小图标，默认不抢正文注意力；可展开内容应有明确的展开 / 收起状态。
- 内容滚动时，顶部标题使用渐变保护可读性；固定区域不可遮挡正文或输入焦点。
- 后续支持 Markdown、代码块、引用、表格、文件等时，须单独定义状态、排版和溢出规则；当前原型不构成完整富文本规范。

### 8.4 输入框

- 输入容器现状圆角 **28px**、1px 边框；聚焦时边框及阴影增强。
- 文本区上内边距 6px，下内边距 10px；发送与工具按钮所在行应与底部边界保持可见留白。
- 单行起步，内容增多时自动增高；设置合理的最大高度与内部滚动，避免挤掉聊天内容。具体最大高度需在实际设备验证。
- 输入区工具按功能分组，发送为明确的最终操作；禁用、可发送、发送中和失败状态需分别设计，不仅依赖颜色。
- CodeMova 新聊天可显示“项目 / 此计算机”上下文条；它用于告知当前上下文，不应与输入表面视觉脱节。
- 输入区使用第三方组件及独立样式，扩展时先通过现有主题和 `composer-dark.css` 覆盖，不直接修改 vendor 打包代码。

### 8.5 按钮、开关、输入和反馈

- **主按钮**：每个局部任务突出一个主要动作；文字明确，背景可见。默认、hover、pressed、focus、disabled 都要定义。
- **次按钮**：优先文字或低强调底色；不能看起来比主按钮更重要。
- **图标按钮**：固定命中区域、居中图标、hover 背景、可见焦点；无文字时提供无障碍名称。
- **开关**：用于立即生效的二元状态；文字描述状态，不能仅靠颜色或位置；支持键盘与屏幕阅读器。
- **输入框**：有持久标签或程序化名称；默认、聚焦、错误、禁用和只读状态明确；错误信息靠近字段并解释如何修复。
- **空状态**：简短说明当前没有什么，以及必要时提供下一步；搜索无结果与真正无数据需区分。
- **加载 / 完成 / 失败**：用文字和适当图标表达；不要只显示无限旋转动画。重试、取消和完成反馈视实际业务设计。

## 9. 动效设计

### 9.1 思路

动效用于解释**从哪里来、发生了什么、现在在哪里**，而不是装饰。局部状态变化要快；面板出现要有轻微位移和透明度变化；可拖拽部件可以有有限的物理反馈。动作不能阻碍连续操作、改变阅读顺序或掩盖系统状态。

### 9.2 时长与曲线

| 场景 | 当前实现 | 后续使用建议 |
| --- | --- | --- |
| 普通按钮颜色 / 背景 | 约 140–150ms `ease` | 立即反馈，避免大幅位移 |
| 箭头与开关 | 约 180ms | 只表达状态变化 |
| 项目菜单进入 | 160ms `cubic-bezier(.22,.9,.26,1)` | 小幅上移 / 缩放与淡入 |
| 设置页、临时侧栏 | 180ms，同类缓出曲线 | 保持起点与空间来源一致 |
| 模型 / 用量面板视图 | 200ms，同类缓出曲线 | 小幅纵向位移，不跨越大段距离 |
| 聊天详情卡 | 220ms `cubic-bezier(.2,.85,.25,1)` | 轻量淡入并接近对应聊天 |
| 长标题滚动 | 延迟 320ms；`max(540ms, 距离 × 19ms)` | 仅标题溢出且指针悬停时播放；离开还原 |
| 思考文字光扫 | 2.4s 线性循环 | 仅真实处理时出现；不作为唯一状态提示 |
| 侧栏拖拽 | 实时跟手、释放后弹簧回位 | 拖拽中位置应直接跟手；回弹幅度受限 |

详情卡现状悬停延迟约 440ms，键盘聚焦约 180ms。若产品后续调整延迟，应统一同类提示并避免阻塞关键操作。

### 9.3 运动规则

- 优先使用 `opacity`、`transform`；动画不应改变邻近布局或造成文本突然跳动。
- 小浮层位移保持在几像素范围；从触发源附近出现，关闭应及时。
- 同一事件避免多个元素同时朝不同方向运动；组件状态要先可理解，再考虑表现力。
- 长标题滚动仅在确实溢出时执行，完整标题仍可通过详情获取；聚焦、窗口变化和离开后应恢复或重新计算。
- 分隔线支持拖拽、方向键和双击恢复。当前键盘方向键步长 16px、Shift 步长 48px；Home / End 到边界。当前 JavaScript 最小 176px、最大受窗口约束，向左超出最小值 24px 可触发收起。实际可用边界以 `sidebar-resize.js` 为准。
- 情绪球为辅助状态角色，待机包含呼吸、眨眼和视线变化；不能用其动作替代必要文字反馈。当前只接入待机，其他情绪不可描述为已完成的业务联动。
- 页面不可见时暂停非必要持续动画；动画不能阻止操作或影响输入。

### 9.4 减少动态效果

遵循 `prefers-reduced-motion: reduce`：取消持续光扫、标题自动滚动、装饰性位移和弹簧，状态直接切换；保留必要的文字、焦点和进度反馈。现有组件已有部分降级，但所有新增动画都必须单独验证，包括 JS 动画与第三方 Shadow DOM 内的动画。

## 10. 响应式与窗口行为

### 10.1 当前断点

| 范围 | 现状 |
| --- | --- |
| `max-width: 850px` | 主区域与侧栏应用窄屏调整；默认侧栏宽度 214px |
| `max-width: 620px` | 侧栏采用窄屏布局；聊天列宽变为 `100% - 20px` |
| `min-width: 621px` | 使用可调桌面侧栏和分隔线；支持收起后的临时预览 |
| `max-width: 860px` | 设置页及模型表单另有窄屏调整 |
| `max-height: 560px` | 对高度受限窗口进行调整 |

桌面默认侧栏宽度现状为 `clamp(214px, 27%, 400px)`；手动调整的边界由容器宽度和脚本约束。断点是当前实现，不代表所有尺寸已经完成可用性验证。

### 10.2 响应式原则

- 在内容宽度不足时优先收起辅助导航、缩短非关键标签；不通过持续缩小正文字号解决布局问题。
- 输入区、对话框和浮层不得超出可视区域；触屏中悬停专属操作必须有替代。
- 项目名、聊天标题、模型名需要在窄宽度下正确省略或换行；不可覆盖归档、发送等操作。
- 桌面分隔线应有可发现的悬停 / 焦点反馈；移动布局不强行保留鼠标式拖拽。
- 适配浏览器缩放、系统字体缩放和不同语言长度；不要把 `--u`、像素截图和设备像素混为一谈。

## 11. 无障碍与输入方式

以下为**目标验收标准**，不表示当前原型已经全部达标：

1. 正文和必要的文本信息按 WCAG 2.2 AA 检查；通常正文至少 4.5:1，大号文字至少 3:1。状态图标、边框和焦点指示也应按适用的非文本对比要求检查。
2. 所有功能可用键盘完成，焦点顺序符合视觉顺序；焦点始终可见，不被裁剪或浮层遮盖。当前全局焦点环为 2px `#5b9bf0`，对不同背景仍需实测。
3. 图标按钮有准确名称；项目展开使用 `aria-expanded`，当前聊天使用 `aria-current`；有状态的控件同步暴露状态。
4. 菜单、对话框和提示使用对应语义；悬停卡不能承载仅鼠标能访问的必要信息。详情使用 `aria-describedby` 时需检查内容重复播报和关闭时机。
5. 错误、加载、成功和选中不只依赖颜色；动态反馈在需要时通过合适的状态区域通知辅助技术，避免频繁打断。
6. 支持触摸、键盘、指针；隐藏的操作不能在触屏上永久不可见，命中区域不重叠。
7. 尊重系统减少动态效果设置；不自动播放可能影响阅读的持续运动。
8. 文本放大、浏览器缩放和窄窗口下，不截断不可恢复的信息，不产生无法关闭的浮层。

## 12. 层级与定位

现状存在多个局部层叠上下文，不能仅凭数值推断全局覆盖关系。已知参考值：聊天顶部渐变 3、标题 4；输入区域 20；聊天详情 / 操作浮层 60；设置视图 70；项目菜单 80。输入组件内部的 30 属于其自身上下文，并不必然高于外层 60。

**目标层级策略**：普通内容 < 固定标题 / 输入区 < 侧栏临时浮层 < 提示与菜单 < 全屏设置 / 对话框。具体层级应集中定义并验证：

- 弹窗边缘保留至少约 10–12px 视口安全距离；空间不足时调整方向并限制高度。
- 与触发元素保持短距离；窗口缩放、侧栏拖动、列表滚动时重新定位或关闭。
- 浮层不得在祖先 `overflow: hidden` 中被意外裁切；必要时放到合适的顶层容器。
- 同时打开多个互斥菜单时先关闭旧菜单；关闭后恢复适当焦点。

## 13. 内容、数据与状态规范

- 本地 / 云端、模型、用量、项目及会话标题均以实际数据为准；原型中的示例值不可当作生产数据。
- 归档、恢复、删除、移除项目必须区分含义：归档应有恢复路径；永久删除和移除项目需要明确告知影响范围，并按实际风险设计确认与恢复机制。
- 明确反馈动作结果；异步操作要考虑进行中、失败、重试、取消及重复点击。
- 不用“成功”等笼统文字代替具体结果；必要时标明对象，例如“已归档：聊天标题”。
- 时间格式在同一视图中统一；相对时间需要能获得准确时间。时间戳和地点尚未在所有原型数据中完整实现。
- 文本默认可本地化，预留中英文长度差异；不能把文案长度写死为布局前提。

建议实施顺序：

1. 保持现有视觉不变，先整理颜色 / 间距 / 圆角 / 动效 token，并建立语义别名。
2. 整理侧栏列表及项目菜单：统一对齐、间距、状态、图标和焦点；移除不可达的历史菜单逻辑。

4. 逐一补足键盘、触屏、溢出、窄屏与减少动态效果；修复实测对比度问题。
5. 把设置、消息、弹窗迁移到统一组件；每次只迁移一组并对照截图与交互验收。
6. 为尚不存在的成功 / 警告 / 错误反馈、富文本、上传、真实网络状态建立独立规范，再实现。

不要为了形式统一一次性替换所有颜色：先建立映射、确认视觉差异和对比度，再逐步收敛。当前 `styles.css` 中有重复声明和后续覆盖，修改前应检查最终生效规则；`composer-dark.css` 中的主题变量也需要从组件作用域读取。

## 16. 当前差异与待决事项

1. 侧栏仍有 `--u` 缩放值和固定 px 混用；滚动条对称留白依赖当前浏览器实现，需要跨平台核验。
2. 菜单、详情卡和输入区浮层的背景、字号和动效来自不同组件，本文给出统一方向，迁移应逐项验证。
3. 项目菜单“归档”会作用于该项目的聊天；短标签在缺少上下文时有歧义，正式产品需要明确反馈、影响范围及恢复方案。
4. 旧聊天操作菜单代码可能仍存在，但当前聊天行直接触发归档，不应把旧菜单当作可用交互。
5. README 部分描述可能滞后于当前代码，例如归档入口和输入上下文；以生效代码与已确认需求为准，后续应同步更新。
6. `#868686` 等低强调色、12px 小字、焦点环和图标对比度尚未经系统性测量；发布前应在真实背景上验证。
7. 对话详情、项目菜单和输入浮层的键盘操作、焦点返回、触屏行为尚需完整测试；不能因为存在 `aria` 属性就认定已达标。
8. 成功、警告、错误、上传、联网状态、浅色主题、跨平台窗口行为等尚无完整设计，不得将本文示例视为已经实现的规范。
